## [0.1.6] - 2026-08-11

### Added

- feat: **`oxionnx-coreml`: `MlPackageModel::ensure_compiled(path) -> Result<PathBuf>`** — compile a `.mlpackage` into the crate's persistent on-disk cache and return the resulting `.mlmodelc` directory *without* loading the model, so an installer or first-run setup step can pay CoreML's compile cost up front instead of inside the first request. Present on the non-Apple stub too (returning `CoreMLError::UnsupportedPlatform`) for API parity.
- feat: **`oxionnx`: `Session::run_gpu_async` — a genuinely asynchronous GPU execution path, awaited rather than blocked on, and a distinct thing from the existing thread-per-inference `run_async`/`spawn_run`/`block_on`.** That pre-existing trio (`session::async_run`) spawns the ordinary blocking `Session::run` onto a background OS thread; it does not, and cannot, help a target with no OS threads at all. `run_gpu_async` (new, `src/session/run/sequential_async.rs`, ~932 lines) is a second, smaller node-execution loop that runs the same nodes in the same order and differs in exactly one place: a node the wgpu backend accepts is `.await`ed instead of blocked on, so the calling task yields to an event loop while the GPU works instead of blocking a thread that may never block on a GPU fence — every thread a browser page has. Underneath, `try_gpu_dispatch_async` (`src/session/gpu_dispatch.rs`) is now the real dispatcher; the synchronous `try_gpu_dispatch` is reduced to a `pollster::block_on` wrapper around it, and every kernel in `oxionnx-gpu` follows the same shape — an `async fn` ending in `read_back_and_recycle_async`, with a thin blocking wrapper — so native and browser targets run identical code instead of two independently drifting copies of the same shape/attribute validation. `block_on_gpu` (`oxionnx-gpu/src/device_guard.rs`) is the seam for that crate's own kernels: `pollster::block_on` natively, and on `wasm32` it drops the future **unpolled** — nothing submitted, allocated or uploaded — so an unconverted kernel fails safe instead of silently no-opping. `Session::enable_gpu_async()` is the paired async device-acquisition step (`session.enable_gpu_async().await` then `session.run_gpu_async(&inputs).await`), needed because acquiring a GPU adapter is itself a promise a session's synchronous constructor cannot block on. The dispatch table gained real arms for `Sub`, `Div`, `PRelu`, `Pad`, `Resize`, `Gemm` and the new fused `OxiInstanceNorm` op in the same wave, tracked in the single `GPU_DISPATCH_OPS` array both dispatchers' capability checks consult. Per-run `GpuRunStats` (GPU/CPU node counts, read-back count and bytes, per-op CPU fallback timing, weight- and activation-residency counters) accumulate on a thread-local, retrieved via `take_run_stats()`/`run_stats()`; `Session::gpu_device_error()` and `gpu_uploaded_bytes()` round out the new accessors. `examples/r3a_cost_breakdown.rs` and `examples/r3a_inswapper_residency.rs` are the measurement harnesses this and the size-gate entry below were sized from. This is proven on native targets only so far — see the "Fixed" entry below for the exact native/browser coverage split.
- feat: **`oxionnx-gpu`: session-lifetime GPU weight residency — convolution and `Gemm` weights now cross the host↔device bus once per session instead of once per dispatch.** A graph's initializers (`Conv`'s `W`/`B`, `Gemm`'s `B`/`C`) never change between frames, but every prior dispatch rebuilt their device buffers from the host tensor anyway; InSwapper-128 alone re-uploaded 502.7 MB of invariant convolution weights on every forward pass, and ArcFace's embedding head is a 51.4 MB `Gemm` `B` by itself. `oxionnx_gpu::context::resident::ResidentBuffers` (new, `oxionnx-gpu/src/context/resident.rs`) now caches a `TrackedBuffer` per caller-supplied identity for the life of the `GpuContext`, checked rather than trusted: each entry records the kernel-slot label and byte length it was uploaded for, and a lookup that disagrees with either (`Lookup::Conflict`) uploads for that one dispatch instead of silently serving the wrong bytes under a reused key. The session layer supplies the identity: `initializer_key` (`src/session/gpu_dispatch.rs`) resolves a node input to a stable, unambiguous graph-initializer name (never a value a node produced this run), and `keyed_operand_slot` restricts caching to the two `(kernel, slot)` pairs that actually bind it — `Conv`'s weight/bias, `Gemm`'s `B`/`C`. `gpu_conv2d_fused_placed_async` and `gpu_gemm_nt_placed_async` are the entry points the dispatcher calls with a `WeightKeys` built from those identities. The cache is additionally keyed per numeric format (`WeightFormat::F32`/`F16`), so a weight resident as `f32` and later requested as `f16` is a miss that uploads the second copy rather than the wrong bytes — what makes flipping `Session::set_f16_compute` mid-session safe. It lives on `GpuContext` itself, not beside the session, because `session::gpu_owner` already creates and destroys a `GpuContext` on one dedicated thread (a cross-thread destroy reproduced a driver `SIGSEGV`), and a residency map held anywhere else would destroy its buffers on whatever thread happened to drop the session's last `Arc`. Observable via `Session::gpu_resident_bytes()` and per-run `GpuRunStats::{weight_cache_hits, weight_cache_misses, weight_upload_bytes}`, and confirmed by 5 device-backed tests in `oxionnx-gpu/tests/r3b_weight_residency.rs` asserting that a second run against the same context uploads exactly zero bytes of a previously-seen weight.
- feat: **`oxionnx`/`oxionnx-gpu`: run-scoped GPU activation residency — a value one GPU node produces can now stay in its device buffer for the next GPU node to consume in place, instead of a read-back and re-upload at every node boundary.** This is the other half of the transfer problem weight residency didn't touch. `src/session/gpu_activations.rs`'s `RunActivations` (new) computes, before a run's first node executes, which node outputs may be produced straight onto the device: a name qualifies only if it is not a graph output (those must still be read back, or `take_outputs` cannot find them), some node actually consumes it (a dead output held resident pins bytes for nobody), and **every** consumer can bind it in place in the exact slot it reads it from — via `op_accepts_resident_slot` in `gpu_dispatch.rs` — with one incapable consumer disqualifying the name entirely, since otherwise the round trip is only moved to a later node, not removed. Values an `If`/`Loop` subgraph captures are always excluded, since a subgraph body runs on the CPU and never appears in `node.inputs`. Lifetime is deterministic, not policy-driven: `RunActivations::new` precomputes each name's last-consumer index across the node order, and `release_after` destroys (returning its budget bytes) every activation whose last use was the node that just ran, so a run always ends with live GPU bytes back at the resident-weight baseline. The new `oxionnx_gpu::context::activation` module supplies the primitives this rests on — `DeviceTensor` (a budget-accounted device buffer plus shape), `TensorSource` (an operand that is either a host slice or a borrowed device buffer), and `OutputPlacement`/`GpuOutput` — which let a kernel's tail, `device_guard::finish_output_async`, either read back to a host `Tensor` as before or hand back a `DeviceTensor` with no staging buffer, no copy and no fence wait. `gpu_conv2d_fused_placed_async`/`gpu_gemm_nt_placed_async` take this alongside `WeightKeys`, so one dispatch call serves both residency mechanisms at once. A consumer that turns out to need a resident value on the host after all (a runtime decline, an unsupported shape) triggers exactly one `read_device_tensor_async` read-back, memoized into the run state. Toggle with `Session::activation_residency_enabled()`/`set_activation_residency()` — off reproduces pre-residency behavior exactly, which is what lets the mechanism be A/B-measured within one session. Confirmed by 5 end-to-end tests in `src/session/tests/gpu_activation.rs`: bit-identical output with residency on vs. off on a `Conv → Relu → Conv → Add` chain, strictly less bus traffic with it on, and the live-byte total returning exactly to baseline once the run ends.
- feat: **`oxionnx`: a new optimizer fusion pass recognizes decomposed AdaIN-style spatial normalization and collapses it into a single `OxiInstanceNorm` op.** PyTorch cannot export `InstanceNormalization` for AdaIN generators — that op requires initializer-shaped `scale`/`B` operands, but AdaIN's per-channel scale and shift come from a runtime Gemm head — so exporters instead emit eight bare-arithmetic nodes: `ReduceMean(axes=[2,3]) → Sub → Mul(diff,diff)|Pow(diff,2) → ReduceMean(axes=[2,3]) → Add(eps) → Sqrt → Reciprocal|Div(1,·) → Mul(diff,·)|Div(diff,·)`. `src/optimizer/fusion/instance_norm.rs` (`fuse_instance_norm`) matches every spelling of that chain — both square forms, both reciprocal/direct-divide forms, either operand order — and rewrites it to one `OxiInstanceNorm` node, eliminating seven intermediate tensors per chain, including `diff` (materialized in full and read three times; `[1,1024,32,32]` in the widest block of its motivating case, the inswapper-128 face-swap decoder, where 12 such chains collapse out of 238 nodes). It runs deliberately after `fuse_layer_norm`: on a 4-D tensor `axes=[2,3]` is also the trailing-axis run `[-2,-1]`, so the two patterns are shape-indistinguishable at the `ReduceMean`, and LayerNorm — which can fold the trailing affine term this pass cannot — gets first refusal; the pass itself only fires once the active registry resolves `OxiInstanceNorm` (true by default, since `OxiInstanceNormOp` is registered in `default_registry()`) and runs within the `PassLevel::Extended`+ fusion block. The fused op (`oxionnx-ops/src/registry/oxi_instance_norm.rs`) computes `(x - mean) / sqrt(var + eps)` per `(n, c)` plane with no affine term, using the same two-pass variance the deleted chain used rather than the one-pass `mean(x²) - mean(x)²` form that loses catastrophically at large magnitude; it is rayon-parallel above 8192 elements and implements `execute`/`execute_inplace`/`execute_into_slots`, all three cross-checked to agree. A matching GPU kernel (`oxionnx-gpu/src/shaders/instance_norm.rs`) reduces one `(n, c)` plane per 256-thread workgroup in shared memory, structured like the existing LayerNorm shader. A new end-to-end test resolves the real inswapper-128 model and asserts exactly 12 chains fuse; a new CPU↔GPU parity test compares the two shipped kernels directly, rather than each one's own unit tests against a separately maintained reference.
- perf: **`oxionnx-gpu`: a direct implicit-GEMM Conv2D kernel replaces a CPU/GPU hybrid that was measurably slower than the CPU operator it was meant to accelerate.** The old path (`compute.rs`'s hybrid) ran im2col on the CPU and only the GEMM on the GPU, with bias and activation applied back on the CPU — measured at 0.33-0.58x the rayon CPU operator's speed on Metal, because the column matrix it re-uploaded per call is `kH*kW` times the input (InSwapper's twelve `Conv[1024,1024,3,3]` layers: a 4 MB input tile blows up into a 37.7 MB column matrix, ~595 MB of im2col crossing the bus per frame against ~50 MB for the input alone). The new kernel (`oxionnx-gpu/src/shaders/conv2d.rs`, `gpu_conv2d_implicit`) never materializes a column matrix — the im2col gather happens in-register inside the shader as the input tile is staged into workgroup memory — and fuses bias and activation into the epilogue. It walks the K axis (`C_in * kH * kW`) as an explicit `(ky, kx, ic)` loop nest rather than a flat index requiring four integer divisions per staged element, sharing its 64×64 macro-tile / 4×4 register-tile / `vec4`-blocked shared-memory scheme with the existing tiled-GEMM kernel, tuned for InSwapper's large conv-as-GEMM shapes (`M=1024, N=1024, K=9216` for its dominant layer). Measured on M3 via the new `examples/c3_conv2d_gflops.rs` benchmark: ~692 GFLOP/s at the 128×128 decoder layer. `group > 1` convolutions and any shape the device can't bind still decline to the old hybrid path. Correctness is locked in by new `oxionnx-gpu/tests/c3_conv2d_parity.rs` (870 lines) against the actual Conv inventory of three production models, read directly out of their `.onnx` files rather than assumed (InSwapper 20 nodes, ArcFace 53, SCRFD 57 — correcting a task sheet's stated 58), plus ragged and degenerate shapes those models never produce.
- feat: **`oxionnx-gpu`: four new standalone WGSL kernels — general-broadcast binary ops, a transposed-B Gemm, PRelu, and Resize — each validated against an independently structured CPU reference.** `broadcast_binary.rs` adds NumPy-style broadcasting (up to rank 4) for Add/Sub/Mul/Div, covering the `[1,C,H,W] op [1,C,1,1]` per-channel case that the existing flat elementwise kernels decline outright (49 of InSwapper's 67 Add/Mul nodes broadcast this way). `gemm.rs`'s `gpu_gemm_nt` implements `Gemm` with `transB=1`, tuned for InSwapper's AdaIN heads (`[1..64,512] × [2048,512]ᵀ`, with real `alpha`/`beta` uniforms rather than hardcoded 1.0, and `C` optional, row-broadcast, or a full matrix). `prelu.rs` adds per-channel PRelu, and `resize.rs` adds `pytorch_half_pixel` bilinear and `asymmetric` nearest resize, matching `oxionnx-ops::resize`'s reference coordinate-transform formulas exactly (InSwapper's 2 upsamples plus SCRFD's 2 FPN upsamples). Each is checked in a new test file (`k2_broadcast_binary.rs`, `k2_gemm.rs`, `k2_prelu.rs`, `k2_resize.rs`) against a CPU reference deliberately structured differently from both the kernel's own WGSL and its inline Rust reference, so a formula bug shared between those two would not also hide from the test. Each of the four is built on new shared pipeline infrastructure (`kernel_support.rs`), which memoizes every compiled `wgpu::ComputePipeline` into a thread-local keyed by `(device, label, entry_point)` instead of rebuilding it on every dispatch call; per its doc comment, an uncached rebuild cost 0.18-0.61 ms more per dispatch than an equivalent already-cached kernel moving the same bytes (M3), and across one InSwapper frame this infrastructure's kernels are collectively dispatched roughly 89 times, so caching removes tens of milliseconds of pure shader recompilation per frame.
- feat: **`oxionnx-gpu`: half-precision kernel variants are now derived, not hand-written, from a single `f32` source.** `f16_variant.rs` applies a short, anchored list of textual substitutions to the `conv2d` and `gemm_nt` kernel bodies — weights narrowed to `f16` once in storage, activations narrowed at the point they're read, products evaluated in `f16` and widened to `f32` before accumulation — rather than maintaining a hand-written second copy that could silently drift from the `f32` source it must match. If an edit moves an expected anchor, substitution returns `None` and the kernel simply reports no `f16` variant (falling back to `f32`) instead of risking a silent miscompile; the `f32` source itself stays untouched byte-for-byte. New `w2_f16_compute.rs` (562 lines) validates five properties end to end: `f16` conv2d and `gemm_nt` stay within 55 dB PSNR of their own `f32` result on realistic-magnitude tensors; resident weight bytes with the toggle on are exactly half those with it off; flipping the toggle between two runs on one context never serves one kernel the other's cached bytes; a device without `SHADER_F16` reports the mode off and stays on `f32`; and an `f16` convolution over a device-resident input/output still produces a correct result.
- feat: **`oxionnx-gpu`: new GFLOP/s benchmark and boundary-shape correctness tests for the tiled GEMM kernel.** `examples/h2_tiled_gemm_gflops.rs` measures the existing tiled MatMul kernel's end-to-end throughput (buffer upload, dispatch, blocking read-back — the same cost production code pays) through the public `gpu_matmul_tiled` entry point at `1024³` and `2048³`. Because that public wrapper declines below a 10M-FLOP threshold and falls back to a different kernel below `M/K/N=32`, new `oxionnx-gpu/tests/h2_tiled_matmul_gemm.rs` (352 lines) drives the tiled pipeline directly to reach the small and ragged shapes the wrapper would otherwise route around or skip: degenerate (`1×1×1`), fully ragged (`127×129×63`, off every tile boundary), macro-tile-aligned (`512³`/`1024³`), the smallest case forcing a second ragged tile (`65³`), and a tall-skinny im2col-shaped case (`12800×9×64`), at a mixed tolerance of `|gpu - cpu| ≤ 1e-4 × max(1, |cpu|)`.

### Changed

- perf: **`oxionnx-coreml`: `.mlpackage` compilation is now cached on disk instead of being redone — and leaked — on every load.** `MLModel::compileModelAtURL_error:` compiles into a fresh UUID-named directory under `$TMPDIR` on *every* call and neither reuses nor deletes it; `MlPackageModel::load` called it unconditionally, so every process start paid a full recompile and left the output behind permanently (7,408 orphaned `.mlmodelc` trees totalling 857 GB were measured in one developer's `$TMPDIR`). The compiled bundle is now moved into a stable, content-keyed entry — `$OXIONNX_COREML_CACHE_DIR`, else `$HOME/Library/Caches/oxionnx-coreml`, else `<temp>/oxionnx-coreml`, as `<bundle stem>-<fingerprint>.mlmodelc` — and reused from then on. The key folds the relative path, byte length and mtime of every file in the source bundle (metadata only: content-hashing hundreds of megabytes of weights would cost more than the compile it saves), so replacing a `.mlpackage` produces a new entry rather than reusing a stale compile. Installation is an atomic `fs::rename`, with a stage-then-rename fallback when `$TMPDIR` and the cache root are on different volumes, so concurrent processes racing on the same key resolve to a single complete entry and never observe a partial one; the loser of a race discards its own copy. The framework's temporary directory is renamed away or deleted on every path, including every failure path — that is the leak fix. An unloadable cache entry (a crash mid-install, a reaped directory, an OS upgrade) is evicted and recompiled exactly once rather than bricking the model forever, and a cache that cannot be used at all degrades to the previous behavior rather than failing a load that would otherwise succeed. Beyond skipping the compile, the *stable path* is what lets Apple's own ANE program cache hit across process launches: on an M3, resolving and loading SCRFD + ArcFace + InSwapper costs ~4.34 s from a never-seen path and ~0.14 s warm (30×), measured as compile 57/47/44 ms → 0.15/0.14/0.17 ms and `MLModel` load 493/1193/2503 ms → 39/62/41 ms.
- perf: **`oxionnx-coreml`: output extraction fused into a single pass.** `predict`/`predict_features` used to gather each output's elements into a `Vec<u8>` and then walk that whole buffer again to produce `Vec<f32>` (`chunks_exact(4).map(from_ne_bytes)`, or a per-element `f16::to_f32`), costing one full-size intermediate allocation and one extra traversal per output per prediction. The stride walk and the dtype conversion now happen together inside one `getBytesWithHandler:` block, writing final `f32` values straight into the returned buffer. The walk itself was rewritten around a layout planner (`CopyPlan`) that fuses every trailing dimension it legally can into one contiguous run and carries the source offset incrementally, replacing the old per-element `Σ idx[d]·strides[d]` recomputation; a fully C-contiguous array degenerates to a single bulk copy, and SCRFD's cache-line-padded outputs become one `memcpy` per row. `predict_raw`'s `read_raw_bytes` shares the same planner. Measured on the exact SCRFD `det_10g` output set (nine outputs, 252 k elements, rows padded to 32 elements — all on the strided path): 491 µs → 183 µs per frame for the copy algorithm alone (2.7×); a contiguous 1×3×128×128 InSwapper-shaped output goes 42.8 µs → 8.1 µs. Stride semantics are unchanged and are now pinned by a regression suite that checks both readers against a deliberately naive reference gather over padded fixtures (SCRFD's `[N,1]`/`[N,4]`/`[N,10]` layouts, middle-dimension padding, a non-unit innermost stride, extent-1 dimensions, and an `f16` padded case) — none of which any previous test reached, since every existing fixture was C-contiguous.
- `oxionnx-coreml`: `src/package/macos_impl.rs` gained two sibling modules — `array_read.rs` (output extraction: the layout planner, `read_raw_bytes`, `tensor_from_multi_array`) and `compile_cache.rs` (the on-disk compile cache) — keeping every file well inside the project's per-file line-count policy.
- `oxionnx-coreml`: the model-backed `#[ignore]`d tests in `src/package/tests.rs` now resolve their bundle from `OXIONNX_COREML_TEST_MODEL` (falling back to the historical `/tmp/w600k_r50.mlpackage`) and skip gracefully when it is absent, instead of hardcoding that absolute path and `.expect()`-panicking. One exported variable now drives every model-gated test in the crate.
- perf: **`oxionnx`: a measured two-tier size gate now decides whether a node is worth dispatching to the GPU at all, closing regressions of up to 36x that weight residency alone would have reopened.** `examples/r3a_inswapper_residency.rs` ran all 154 of InSwapper's nodes twice on an M3 — CPU-only, then `Auto` with every op wired and no floor beyond each kernel's own — and found only 3 of 10 dispatched op types actually win on the GPU (`Conv` at 0.44x of CPU time, `Pad` 0.26x, `Resize` 0.28x) while the rest lose, several by more than an order of magnitude (`Mul` 1.13x, `Add` 1.65x, `Gemm` 3.07x, `OxiInstanceNorm` 3.30x, `LeakyRelu` 18.82x, `Div` 28.61x, `Relu` 36.60x). The cause is structural: a memory-bound elementwise op moves the same bytes across the bus twice (upload, then read back) at a measured ~5 GiB/s effective round-trip bandwidth against a rayon-parallel CPU kernel touching them once at ~92 GB/s, plus a fixed ~1.4 ms per-dispatch cost — both sides scale linearly in element count, so no size threshold fixes it while operands are transferring. `gpu_min_transfer_elements` (new, `src/session/gpu_residency.rs`) therefore gates each op by which `ResidencyTier` its dispatch is actually in: under `ResidencyTier::Transferred` the structural losers get `MEMORY_BOUND_TRANSFER_FLOOR = Some(usize::MAX)` — never dispatch while operands cross the bus, a measured claim rather than a tunable — while `Conv`/`Pad`/`Resize`/`MatMul`/`Gemm` keep no session-level floor, since they measured as winners (or, for `Gemm`, have a distinct cause, below). Once every one of a node's operands is already device-resident (`node_residency_tier` requires *all* of them — a `Conv` whose weight is cached but whose activation still uploads does not qualify), the two-times-transfer cost disappears and the same elementwise kernels become worthwhile at any size that fills one workgroup: `RESIDENT_DISPATCH_FLOOR = 256` elements, replacing a previously uncalibrated `4096` chosen by analogy with the wrong cost model. Separately, `GEMM_GPU_MIN_FLOPS` (10 MFLOP) now gates `Gemm` ahead of `gpu_gemm_nt`, which has no minimum-size threshold of its own: InSwapper's 12 AdaIN heads (`[1,512] x [2048,512]ᵀ`, 2.1 MFLOP each, measured 3.07x slower on the GPU) now decline, while ArcFace's 25.7 MFLOP head still dispatches. The FLOP arithmetic behind these gates was also widened from `usize` to `u64` in `oxionnx-gpu/src/compute.rs`'s `GPU_THRESHOLD`/`gemm_flops`: on a 32-bit `usize` target the product for a 2048³ GEMM (8.6 GFLOP) overflowed and silently declined exactly the large multiplies the threshold exists to admit — measured in Chrome as a 2048³ multiply completing in 0.0 ms with no device error, versus a 1024³ one dispatching normally in 7.7 ms.
- **`oxionnx-gpu`: the five pre-existing kernel families — elementwise, normalization, reduction, softmax, transpose — were converted to the same async-first, budget-checked buffer path the new kernel batch uses.** Every dispatch function's real implementation is now `gpu_x_async`, with `gpu_x` reduced to a `block_on_gpu` wrapper; ad hoc `device.create_buffer_init` calls and direct pool locking were replaced with shared `ctx.upload_buffer`/`ctx.pooled_buffer`/`ctx.staging_buffer` helpers; and a new `budget_admits` pre-flight check declines a dispatch outright when it would exceed the context's byte budget, rather than attempting the allocation and finding out. `GpuBufferPool::get_buffer` changed accordingly, from returning `wgpu::Buffer` to a fallible `Option<TrackedBuffer>`.

### Fixed

- fix: **wasm32-unknown-unknown CPU inference actually works now — previous releases only compiled.** Every prior "WebAssembly support" changelog entry (0.1.0, 0.1.4) described `cargo check`/`build --target wasm32-unknown-unknown` succeeding, which is not the same claim as a model running in a browser without panicking; it never did, for two independent reasons that both had to be fixed:
  - **`oxifft`'s default `threading` feature (rayon) is a `compile_error!` on wasm32.** `oxionnx-ops` depended on it via a plain `{ workspace = true }`, which always pulled the default feature set. Fixed by target-splitting the dependency — `[target.'cfg(not(target_arch = "wasm32"))'.dependencies] oxifft = { features = ["std", "threading"] }` (native parallel DFT unchanged) vs. `[target.'cfg(target_arch = "wasm32")'.dependencies] oxifft = { features = ["std"] }` — which additionally required the workspace-level `oxifft` entry to declare `default-features = false` itself: Cargo silently ignores a member's `default-features = false` override on a `workspace = true` dependency whose workspace-level entry leaves `default-features` unspecified (verified empirically; it only warns, threading stays on).
  - **`std::time::Instant::now()`/`SystemTime::now()` compile on wasm32-unknown-unknown but panic the instant either is called** — there is no OS clock without a JS shim, and no `cargo check`/`build` can catch a runtime-only panic. Both were called unconditionally from the model-load path (`session/loading.rs`'s parse/build/optimize/sort/plan stage timers), the per-node dispatch path (`session/run/{dispatch,sequential,parallel}.rs`), and the unseeded-PRNG fallback for `Random*`/`Bernoulli` ops (`oxionnx-ops/src/registry/random_ops/rng.rs`, `dsp/bernoulli.rs`) — all reachable from an ordinary `WasmSession::run_one` call with no GPU/threading feature involved. Fixed with a `time_compat` module in each crate (`oxionnx`, `oxionnx-ops`) that re-exports `std::time::{Instant, SystemTime, UNIX_EPOCH}` unchanged on every other target and swaps in `web-time`'s `Performance.now()`/`Date.now()`-backed drop-ins (identical API, including `Add<Duration>` and ordering) on wasm32-unknown-unknown; every call site now routes through it.
  - **`Session::run_async`/`spawn_run`/`block_on` start inference on a plain `std::thread`**, which compiles on wasm32-unknown-unknown (that target has no OS threads) but panics identically to the above the instant it is called. Nothing on the wasm-facing API (`WasmSession::run_one`/`run_multi`, which call `Session::run` synchronously) ever referenced it, so `session::async_run` — and its `block_on`/`RunFuture`/`RunHandle` re-exports — is now `#[cfg(not(target_arch = "wasm32"))]` in full: a caller reaching for it on that target gets a compile-time "not found" instead of the previous runtime panic. `gpu_owner`'s `atexit`-hook quiescence check (native-only regardless, see below) no longer references the now wasm32-absent worker-count query on that target.
  - Two long-dormant wasm32-only warnings surfaced once the above unblocked the build far enough to reach them (both pre-existing, unrelated to this fix, simply never reachable before): an unused `total_jobs` in `oxionnx-ops`'s N-D convolution (computed only for the rayon path, which does not exist on wasm32) and a never-called `SdpaJob::macs_per_slice` in the attention kernel (same rayon-threshold shape) — both now `#[cfg(not(target_arch = "wasm32"))]`-gated alongside the code that used them.
  - `pollster` (the `gpu` feature's native blocking executor for `wgpu` adapter/device requests) moved from an unconditional optional dependency to `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]`, matching `oxionnx-gpu`'s own `Cargo.toml`, so a future wasm32+`gpu` build does not carry a dependency that cannot do anything useful there.
  - `scripts/check_wasm.sh` added: builds `oxionnx` for wasm32 with the `wasm` feature and `cargo check`s `oxionnx-ops`, the two crates this fix touches.
  - **`--target wasm32-unknown-unknown --features wasm,gpu` now builds.** It did not as of v0.1.5: wgpu's WebGPU backend holds internal `Rc`/`RefCell`/`Cell` state (`WebDevice`, `WebBuffer`, …), which is not `Send`/`Sync`, while this crate's `Session: Send + Sync` compile-time assertion was deliberately unconditional across every feature combination, including wasm32. - fix: **`oxionnx-gpu`: the reusable GPU buffer pool no longer leaks device memory without bound, and every buffer this crate allocates is now checked against a live-byte budget before creation.** Dropping a `wgpu::Buffer` frees nothing on the WebGPU backend — `WebBuffer`'s `Drop` impl is empty (`wgpu` 29.0.4) — so `GpuBufferPool` (`oxionnx-gpu/src/context/tracker_pool.rs`) evicting its LRU entries by dropping bare `wgpu::Buffer`s was bookkeeping and nothing more there: memory kept accumulating until `createBuffer` started failing, which is unrecoverable inside wgpu's web backend. `TrackedBuffer` and `GpuMemoryBudget` (new, `oxionnx-gpu/src/context/budget.rs`) fix this at the allocation boundary: every buffer this crate creates is now a `TrackedBuffer`, which calls `wgpu::Buffer::destroy` and releases its reservation on drop (safe on both backends once `queue.submit` has run), and every allocation reserves its bytes against a shared `GpuMemoryBudget` first, declining rather than allocating once the ceiling (`DEFAULT_LIVE_BYTE_BUDGET`, 1.5 GiB, sized for a browser tab sharing one GPU process with every other tab) would be exceeded — introspectable and adjustable via the new `GpuContext::{live_gpu_bytes, gpu_byte_budget, set_gpu_byte_budget}`. `GpuBufferPool::get_buffer` now returns `Option<TrackedBuffer>` instead of an unconditional `wgpu::Buffer`, and a new `reclaim_for` evicts idle pooled entries — budget-accounted exactly like in-use buffers, since both cost the same driver memory — before declining an allocation outright. - fix: **`oxionnx`: the GPU `Reduce*` dispatch path no longer wraps a negative axis into a huge `usize` or under-reports a fully-reduced tensor's rank.** `normalize_reduce_axes`/`normalize_single_reduce_axis` (`src/session/gpu_dispatch.rs`) used to compute `axis as usize` directly on a negative `i64`, so an axis of `-1` became `18446744073709551615` instead of `rank - 1`; an out-of-range axis now declines the whole dispatch back to the CPU kernel, which reports the error properly, instead of indexing off the end of the shape. Separately, `single_axis_reduce_shape` used to return `[1]` for a full reduction with `keepdims=0` on a rank-1 input, where ONNX (and NumPy: `np.sum(x, axis=0, keepdims=False).shape == ()`) specifies a genuine rank-0 scalar — so the same graph could report a different output *rank* depending only on whether the GPU arm accepted the node or the CPU kernel ran instead, with anything downstream driven by a `Shape` node then seeing one dimension too many; element count was identical either way, only the reported shape was wrong. Both are exercised by the shape/attribute gating unit tests in `gpu_dispatch_tests.rs`'s `gating_tests` module, which run without a live GPU adapter.
- fix: **`oxionnx-ops`: CPU Conv2D's im2col workspace is now capped instead of scaling unbounded with kernel volume × output area.** The column matrix is `[C/group * kH * kW, OH * OW]` `f32`, and for InSwapper's largest layers alone that is 302-411 MB per call, on top of resident weights — on `wasm32`, an unsatisfiable `WebAssembly.Memory.grow` aborts the module outright, and wasm linear memory never shrinks, so a single such request permanently raises the tab's memory ceiling. `conv2d.rs` now caps any single im2col workspace at 64 MiB (`IM2COL_WORKSPACE_MAX_BYTES`); above that, output columns are processed in blocks (`im2col_block`/`im2col_block_maybe_parallel`), each GEMM'd into its own slice of the destination via a new leading-dimension-aware `sgemm_*_ldc` path, with block boundaries rounded to whole output rows wherever possible (the native multi-threaded path still keeps one capped buffer per rayon worker, so aggregate peak is `workers × 64 MiB`, still far below `workers × the uncapped size`). The result is bit-identical to the unblocked path by construction — `matrixmultiply`'s GEMM accumulates with `N` as its outermost loop, so splitting `N` externally cannot change any element's accumulation order — and is asserted as such by new tests (`sgemm_column_blocks_are_bitwise_identical_to_one_call`, `blocked_im2col_matches_the_monolithic_path_bitwise`, `blocked_im2col_matches_on_the_inswapper_worst_shapes`), while convolutions already under the cap keep their exact prior code path and cost. The same cycle also extended the existing `wasm-threads`-gated rayon parallelism convention to `conv_nd.rs`'s N-D im2col path, which had previously hard-disabled rayon on every `wasm32` build regardless of that feature.
- fix: **`oxionnx-gpu`: the WGSL `reflect`-mode `Pad` kernel produced wrong values in the leading padding region on Vulkan/NVIDIA.** `reflect_coord`'s original formula computed a period-`2*(dim-1)` modulo in `i32` and corrected a negative result by adding the period back — `var c = (out_coord - pad_before) % period; if (c < 0) { c = c + period; }` — which assumes WGSL's `%` on a negative dividend returns a negative-or-zero remainder. On Vulkan with the NVIDIA driver (naga 29, driver 550) it does not: `-1 % 6` evaluated to `3` and `-2 % 6` to `2`, the unsigned results for the two's-complement bit patterns rather than a sign-of-dividend remainder, so the `c < 0` correction branch never fired and the leading pad region silently wrapped instead of reflecting (`out_coord=1`, `pad_before=2`, `dim=4` read source index 3 instead of the correct 1; a coincidental match at `out_coord=0` masked the bug there). Fixed by moving the whole reduction into `u32`, on an operand that is non-negative by construction (`raw >= 0` uses `u32(raw) % period` directly; `raw < 0` computes `u32(-raw) % period` and subtracts from `period`, safe because `-raw`'s magnitude is bounded by the tensor extent), so no branch depends on the sign behavior of `%` on a negative operand. `reflect_coord_host` (`k2_pad.rs`) states the same formula in plain Rust as the test oracle, cross-checked against literal NumPy `reflect`-mode output. `w3_gpu_kernel_parity.rs`'s adapter-availability panic message was also expanded to name a second failure mode particular to Linux: `GpuContext` requests `Backends::VULKAN` only there with no GL fallback, so a host with a working NVIDIA driver but a missing loader package (`libvulkan.so.1`, Debian/Ubuntu's separate `libvulkan1`) enumerates zero adapters and fails all 17 tests in the file, which reads as broken kernels rather than a missing system package.

- fix: nested subgraph attributes are now depth-limited instead of allowing unbounded recursion, which could stack-overflow the process on a crafted model.
- fix: lengths read from untrusted model bytes are clamped before sizing an allocation (`vec![0u8; len]` in the streaming reader could previously OOM-abort on a hostile length).
- fix: `TensorProto` typed-data fields now use the correct field numbers and element encodings; non-packed (unpacked) repeated numeric fields, previously silently dropped, are now read; group wire types (3/4) are skipped instead of aborting the whole parse; the varint decoder no longer silently truncates bits above 64 on a 10-byte varint; `TensorProto.segment` is read instead of ignored.
- fix: `GraphProto.sparse_initializer`/`value_info` and `AttributeProto.tensors`/`graphs`/`sparse_tensor`/`type_proto`/`ref_attr_name` are now parsed instead of being unhandled.
- fix: weight decode for uint8/int8/bool/double/bfloat16 initializers no longer silently zero-fills; `STRINGS`-list attributes are wired through graph conversion instead of dropped; external-data `location` is sandboxed against path traversal / absolute-path reads, and its offset/length arithmetic is checked instead of panicking on a reversed or overflowing range; negative or overflowing `dims` are rejected with a typed error instead of being cast to a huge `usize`.

**Spec-conformance fixes** (`oxionnx-ops`):
- fix: `Slice` honors negative `start`/`end`/`step` values instead of ignoring them.
- fix: `Pad` accepts the opset-18 `axes` input (previously panicked), applies negative pads as a real crop (previously clamped to 0), and implements `wrap` mode instead of silently falling back to `constant`.
- fix: `Resize` implements real cubic interpolation (previously silently degraded to nearest-neighbor), honors all `nearest_mode` variants including `round_prefer_floor` (previously always floored, shifting the image by half a pixel), and handles `coordinate_transformation_mode` values it previously ignored (`tf_crop_and_resize`, `tf_half_pixel_for_nn`).
- fix: `GRU` with `linear_before_reset=0` — the ONNX **default** — applied the reset gate at the wrong index; opset-conformant models relying on the default now compute the correct gate.
- fix: `ScatterElements`/`ScatterND` implement the `reduction` attribute (opset 16 `add`/`mul`/`max`/`min` — previously always overwrote regardless of the attribute) and bounds-check indices, including negative indices counted from the end (previously written to row 0).
- fix: `QuantizeLinear`/`DequantizeLinear` honor the `axis` attribute for per-channel scale/zero-point broadcast (previously mathematically wrong for any axis but the last) and derive the saturation range from the target dtype instead of hardcoding an int8 `[-128, 127]` clamp, which corrupted the more common default uint8 case.
- fix: `TreeEnsembleClassifier`/`Regressor` guard against cyclic node tables instead of looping forever on a malformed or adversarial real tree model, route NaN inputs per `nodes_missing_value_tracks_true`, and implement `MIN`/`MAX` aggregate functions (previously silently treated as `SUM`).
- fix: opset-aware `Softmax`/`LogSoftmax`/`Hardmax` semantics — see Added.
- fix: **`DFT`/`STFT` (`oxionnx-ops/src/dsp/dft.rs` + `stft.rs`, both built on `oxifft::fft`/`ifft`) inherit an upstream x86_64 correctness fix** — bumping `oxifft` 0.3.2 → 0.4.2 pulls in a fix for two bugs in the SSE3 SIMD butterfly kernel that every x86_64 CPU without AVX2 dispatched to: a wrong complex-multiply lane order, and twiddle-recurrence drift that broke Bluestein's chirp round-trip for non-power-of-two lengths. On such hosts, `DFT`/`STFT` outputs were wrong by orders of magnitude — a wrong-answer bug, not a precision one. aarch64 (NEON) and AVX2+ x86_64 went through a different, unaffected kernel throughout and were never wrong. This is an upstream fix, not independently re-verified against this repository's own test suite — see `oxifft`'s `CHANGELOG.md` for the root-cause writeup, including its stated caveat that the AVX2/AVX-512 tiers remain hand-audited but have never been executed on real hardware there.
- fix: dozens of additional panics-on-malformed-input closed across shape/reduce axis normalization, `Concat`/`Split`/`Transpose`/`Unsqueeze`/`Expand`/`Reshape` bounds checks, `GridSample`/`RoiAlign` string-attribute parsing (previously read as ints, silently keeping the default), SDPA mask broadcast, `Attention`'s `is_causal`, `LSTM`/`GRU`/`RNN` `clip`/`layout`, `Gelu`/`Clip`/`Cast`/`Mod`/`Bitwise*`/`Dropout`/`GroupNorm` attribute handling, `TfIdfVectorizer` `ngram_counts` + batched input, SVM Platt scaling, and 0-size-dim (empty tensor) handling across the engine — full 16-domain list in `TODO.md` §17 wave 1.

**GPU / CUDA / DirectML hardening**:
- fix: `oxionnx-gpu` dispatch now declines to the CPU path instead of silently producing wrong results on shapes its kernels don't actually support — MatMul dropping batch dimensions, Softmax ignoring `axis`, reduction ignoring `keepdims`, elementwise ops gating on element count instead of shape equality, and fused Conv discarding the optimizer's fused activation are all closed; three previously-disagreeing op-support lists are unified so implemented GPU kernels are actually reachable from the `Auto` placement path.
- fix: `oxionnx-gpu` backend dispatches are clamped to the 65535 `max_compute_workgroups_per_dimension` limit and checked against `max_buffer_size` instead of panicking on large tensors/weights; every wgpu call now runs inside an error scope with CPU fallback instead of panicking on a validation/OOM/device-lost error; blocking readback has a timeout instead of being able to hang forever; `LeakyRelu`'s WGSL kernel reads the node's `alpha` attribute instead of hardcoding `0.01`.
- fix: **wasm32 GPU context creation now honestly declines** (`GpuContext::try_new`/`try_new_async` return `None`) instead of uploading inputs, allocating buffers, encoding a dispatch, and calling `queue.submit` for every node and then discarding the result — blocking `map_async` readback is impossible in the browser, so the previous path was pure overhead that could never produce a value while the CPU silently recomputed the same op. The CPU path now runs directly with no wasted GPU work.
- fix: `oxionnx-cuda` — batch-broadcast `MatMul` operands (e.g. 3-D activations × 2-D weight), `ReduceSum`/`ReduceMax` silently truncating to the first 256 elements of the axis, `Softmax` ignoring the ONNX `axis` attribute, `LeakyRelu`/`HardSigmoid` ignoring the node's `alpha`/`beta`, and `Gemm`'s bias epilogue dropping bias for shapes other than `[N]`/`[M,N]` are all fixed. An `OXIONNX_CUDA_VERIFY` shadow-comparison gate was added, since unlike `oxionnx-directml` this crate previously had no opt-in verification gate and these bugs shipped silently to every CUDA user by default.
- fix: **`decide_placement` is now the single source of truth for CPU/accelerator routing** — its `OpPlacement::Auto` arm previously only ever weighed the wgpu-flavored `is_gpu_capable` against `gpu_threshold_bytes` and could only return `ProviderKind::Gpu` or `Cpu`; `Cuda`/`DirectMl` were reachable only through an explicit `OpPlacement::Manual` pin, never through `Auto`'s size-based heuristic. `Auto` now calls a new `select_accelerator(op)`, which consults each backend's own op-support predicate in priority order `Cuda > DirectMl > Gpu` (`oxionnx_cuda::is_supported_op` / `oxionnx_directml::is_supported_op` / `is_gpu_capable`) and applies `gpu_threshold_bytes` uniformly to whichever it picks — so, for example, `Conv` is never routed to CUDA (which has no CUDA convolution kernel; see below), even though wgpu's `is_gpu_capable` claims `Conv`. `OpPlacement::Manual` pins now also pass through a new hard floor, `MIN_GPU_DISPATCH_BYTES` (4096 bytes = one page = 1024 `f32` elements): an accelerator pin below the floor is overridden back to `Cpu`, since the fixed cost of a discrete-GPU round trip (~20 µs of upload/dispatch/fence/readback) outweighs the entire cost of a CPU elementwise op that small by more than an order of magnitude. New `provider_supports_op(provider, op)` exposes the per-backend predicate directly.
- fix: **`oxionnx-cuda`: dead, silently-wrong `Conv` GPU implementation removed** — `cuda_conv` previously contained a real `oxicuda_dnn::conv::api::conv_forward` NCHW code path (device upload, descriptor construction, bias epilogue) that was already permanently unreachable behind a bare `if true { return Ok(None); }`, because `oxicuda-dnn`'s convolution engines have stubbed GEMM phases and produced numerically wrong results; the dead code is deleted and `cuda_conv` is now an honest, documented, unconditional decline. New `oxionnx_cuda::is_supported_op(op)` reports exactly the 25 ops `try_cuda_dispatch` can claim (`MatMul`/`Gemm`, 16 unary activations, `Add`/`Sub`/`Mul`/`Div`, `ReduceSum`/`ReduceMax`, `Softmax`) and `false` for `Conv` and everything else, so the placement logic above can skip CUDA before paying for an upload/dispatch/readback instead of discovering the decline only after a round trip.

**Core hardening**:
- fix: `oxionnx-core`'s advertised `no_std` support previously failed to build; it is repaired and now compile-verified (`cargo check -p oxionnx-core --no-default-features`).
- fix: `encrypt_bytes` derived AES-GCM nonces from wall-clock time instead of a CSPRNG; nonces are now CSPRNG-sourced.
- fix: topological sort could underflow `in_degree` (a `usize`) when a node's output name collided with a known input/initializer name, or where `in_degree`/`dependents` were built under inconsistent conditions.
- fix: `Tensor::new` only validated `data.len() == shape.iter().product()` in debug builds; the new fallible `Tensor::try_new` validates unconditionally, including release builds, and returns a typed `OnnxError::ShapeMismatch` instead of risking a panic or silent corruption from untrusted model bytes. `Tensor::new`'s signature and infallible behavior are unchanged for callers who can guarantee the invariant statically.
- `deny.toml` added at the workspace root, enforcing the COOLJAPAN banned-crate list via `cargo deny check bans`.
- fix: `oxionnx-proto`: `AttributeProto.strings` (`repeated bytes strings = 9`) was re-parsed as a nested protobuf message instead of being read as a raw string, corrupting ONNX-ML `TreeEnsemble` models whose `nodes_modes` values (e.g. `"BRANCH_GTE"`) happen to start with bytes that decode as a plausible tag + length prefix — raised a spurious `length-delimited: EOF (need 82, have 8)` error. Field 9 entries are now pushed verbatim, with a regression test covering the reported case (#3).
- fix: `oxionnx-coreml`: `compute_plan_summary()` only walked the `MLProgram`'s `"main"` function, silently under-counting models that declare additional functions (e.g. stateful submodels). Both `compute_plan_summary()` and the new `compute_plan_breakdown()` now iterate every declared function.
